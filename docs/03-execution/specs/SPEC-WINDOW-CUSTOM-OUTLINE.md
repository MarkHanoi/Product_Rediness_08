## 0. The founder's brief (verbatim intent)

> In the window type editor we have an amazing 3D viewer. Add a projection ELEVATION (looking at the window from the front) and use the wall-editor technology to define the PERIMETER of the window — triangular windows, non-rectangular, non-circular, and further. The principle is always: a frame, a sill and glass; every other parameter stays part of any possible shape. Maximum flexibility with the shape.

## 2. Decisions

**D1 — One shape axis, one new kind, one companion carrier.** `openingProfile` gains the kind **`'custom'`**. The ring travels in a companion field on the SAME host record, `customOutline: { vertices: { u: number; v: number }[] }`, present **iff** `openingProfile === 'custom'` (Zod refine, all three schemas: `WallDataSchema`, `WindowTypes`, `DoorTypes` — Zod strips undeclared keys, so all three or it dies on load). This amends **PR-7** ("one field") to "one AXIS: the kind, plus its carrier, which no other kind may populate".

**D2 — The ring is NORMALISED to the unit bounding box.** `u, v ∈ [0, 1]`, `u` along the wall, `v` up from the sill line. `width × height` therefore REMAIN the only size vocabulary (PR-8's purpose — occupancy, drag, `W×H` grammar, plan extent, IFC all keep working unchanged). Consequence, stated as the rule: *a custom shape is defined relative to its opening's bounding box; resizing the opening stretches it.* The type editor authors at the type's default `width × height`, so the user draws true proportions.

**D3 — Validity of a ring (L2 `validateCustomOutline`, the ONE predicate, three askers: schema refine, editor commit gate, `openingProfileShapeRefusal`).** ≥ 3 vertices · simple polygon (no self-intersection; reuse `geometry-kernel` `findSelfIntersection`) · CCW (normalise on commit, never refuse for winding) · first vertex not repeated · TIGHT bbox: some vertex on each of `u=0`, `u=1`, `v=0`, `v=1` within `1e-6` (else `width/height` would lie — C84 EI-9) · area ≥ `PROFILE_MIN_AREA` as a fraction of the unit box, justified from `WallProfile.PROFILE_MIN_AREA_M2` at the type's default size · arcs are TESSELLATED at authoring (`arcSegmentThroughMidpoint`, the boundary tool's 16 chords; recoverable later by `resolveBoundarySegments`) — no `curve` field, the repo's established convention (F2). Every refusal names the failing rule and the numbers (C74, CA-18).

**D4 — Frame, sill, glass are DERIVED, never authored (C75).** Frame = `insetOutlinePoints(ring·(w,h), frameThickness)` → `profiledBandGeometry`; if the inset returns `null` the type editor refuses BY NAME ("the frame inset of 60 mm fails at vertex 3 — reduce the frame thickness or open the angle") and the commit gate holds. Glass = `profiledPlateGeometry` on the sash inset. **Sill = the lowest horizontal straight run of the ring** (the edge(s) at `v = 0` with length > 0): a sill board of that run's length + `sillOverhang`; a ring whose bottom is a vertex or an arc (apex-down triangle, circle) gets **no sill, reported by name** in the preview and the properties panel — the founder's "always a sill" is honoured wherever a sill can physically sit, and refused audibly where it cannot. Glazing grid on the profiled arm stays ABSENT and stays declared (F8) — not widened by this spec.

**D5 — Wall arms.** A: consumes the ring directly (PR-3; window = hole, `sillHeight > 0` required — a custom ring reaching the floor is a NOTCH and is refused for windows with the door alternative named). B/C: bbox + gasket — the gasket is `bbox − outline`; the lane MUST measure a concave ring (e.g. an L or a star) through `OpeningProfileGasket` and `LayeredWallOpeningBuilder` and pin it (PR-4: every reveal face on the outline, none on the bbox inside the opening). D: refuses (unchanged). E: excluded (unchanged, pinned both ways).

**D6 — Type template, instance owner (reconciles F7).** `WindowSystemType` gains optional `customOutline` (the normalised ring). A window CREATED while the active type carries one is created with `openingProfile: 'custom'` + a COPY of the ring on its `Opening`. Changing the type of an EXISTING window does NOT reshape it (L-10948 stays literally true); the properties panel offers **"Apply shape from type"** as an explicit, undoable command. Editing the type's outline later does NOT reach existing instances (C65 §3.6 defect avoided) — that is the price of the ruling, stated in the ADR. This is a C86 §10.5.b amendment: *a shape TEMPLATE may live on the type; the instance owns its ring.*

**D7 — Authoring surface (C86 §10.5.a, four surfaces or a recorded blocker).** Type editor: an "Elevation outline" section (new registry capability `finishEditor.outline` — a declaration, never a family branch, C65 §3.5) mounting the generalised outline editor with modes **Rectangle (reset) · Polyline (click-to-place, Enter closes, ⛔ ORTHO absolute when on) · Arc (3-click through midpoint) · Presets (triangle, trapezoid, gable/pentagon, gothic)** — presets are just rings, they carry no code. Pre-draw picker: shows `custom (from type)` as a read-only pill when the type carries a ring. Inspector (`WindowSection` Shape row): lists `custom` only when the instance has a ring, plus "Apply shape from type" / "Edit outline…" (opens the same editor on the instance's ring, at the instance's `width × height`). Data Workbench: displays the kind; ring editing there is a RECORDED omission.

**D8 — 3D preview.** `PreviewSubject` gains a part kind `extrudedOutline { points: {x,y}[]; depth; center; holes? }` (THREE-free, L-free data) and `ElementPreviewRenderer` extrudes it on the P2-legal path. Frame band, glass plate and sill of a custom type render from the SAME derivations as the builder (D4) — `buildOpeningPreviewSubject` calls the geometry-window derivation, never a copy (C84 EI-11).

**D9 — Drawings.** Elevation symbol: inset via `insetOutlinePoints` for ALL profiled kinds (fixes F9 by construction). Plan symbol: the cut width at the section plane is read from the outline at `cutHeight − sillHeight` (a circle cut above its centre is narrower than its bbox) — for every non-rectangular kind, not only `custom`; where the plane misses the ring the symbol is omitted with a CA-18 note. IFC: `IfcWindow` export of a non-rectangular opening is DECLARED (C84 §12 / C25 §1.9 row: "shape not represented — bbox rectangle exported; profile kind in `Pset` description") — the rectangle silhouette that already ships for arches becomes a NAMED absence instead of a silent one.

**D10 — Chat / RAC (C67/C68).** `'custom'` is registered in `OpeningShapeVocabulary` as a kind that is NOT claimable by adjective ("make the windows custom" → refusal naming the type editor); presets ARE claimable by name through the catalogue ladder (`triangular`, `trapezoid`, `gable`, `gothic`) and resolve to the preset ring — table rows, zero new resolver arms. RAC matrix row for `window.customOutline`: askable (vertex count, bbox tightness), settable only via type/preset.

**D11 — Persistence / undo.** Additive optional fields on `Opening` (three schemas), `WindowSystemType` (`hostedSystemTypeCodec`, `ProjectSerializer`), `declaredProjectScopes` unchanged. C47: additive-optional ⇒ no `SCHEMA_VERSION` bump — the lane VERIFIES against the migration policy and records the verdict. `CreateWallOpeningCommand` carries the ring in its existing dual write (C15 §8.1 gate). **L-3421 is closed in the same lane** (`WallStore.updateWindow` self-heal must carry `openingProfile` AND `customOutline`). `affectedStores` unchanged.

**D12 — Doors.** Out of scope: `openingProfilesFor('door')` does not offer `custom` (a door is a floor notch; `notchWalk` assumes two feet). Recorded, with the alternative named.

## 5. Acceptance (what the founder will see)
1. Window type editor → "Elevation outline" → draw a triangle (3 clicks, Enter) → the 3D viewer shows a triangular frame, glass, and a sill on the base run → Save type.
2. Draw a window with that type → the wall shows a triangular hole with reveals on the true outline (plain and LAYERED walls) → elevation view shows the triangle with its frame line; plan symbol at 1.2 m cut shows the cut width.
3. Apex-down triangle → preview states "no sill: the outline has no horizontal base run" and still builds frame + glass.
4. A self-intersecting outline is refused at commit with the crossing named; a 60 mm frame on a 20° corner is refused with the vertex named.
5. Undo after creating the window removes it from BOTH stores; reload keeps the shape; changing an existing window's type does not reshape it; "Apply shape from type" does, and undoes.
6. Chat: "change all windows to type Gable" works; "make all windows triangular" resolves to the preset; "make the windows custom" is refused naming the type editor.

## 6. The authoring technology — the wall PROFILE editor, reused (founder-ratified 2026-08-25)

**This is the technology, not the plan-tool overlay and not a 3-D handle editor.** Ratified by the founder on the mapper's finding; carried into the contract as **C86 §10.6** by OUTLINE82 (this section is the working copy — the contract wins if they ever differ).

- **L7 UI:** `apps/editor/src/ui/WallProfileEditor.ts` (569 lines) — SVG surface, draggable/resizable modal, vertex handles, midpoint-insert handles, double-click delete, Shift = free, Esc/Enter.
- **L2 model:** `packages/geometry-wall/src/WallProfileEditor.ts` (123 lines) — `WallProfileEditorSubject {wallId, length, height, ring}` (`:49`), `WallProfileEditorCallbacks` (`:59`), `WallProfileEditorPort` (`:86`), `WALL_PROFILE_SNAP_M = 0.05` (`:104`), `wallProfileEditorSnap` (`:108`), `wallProfileEditorRectangle` (`:117`).
- **It already draws in an abstract metric ELEVATION frame.** `WallProfileVertex {u, v}` (`packages/geometry-wall/src/WallProfile.ts:223`) — `u` along the baseline, `v` up from the base. The px↔metre map is stated ONCE at `apps/editor/src/ui/WallProfileEditor.ts:222-232`: `x = pad + u·scale`, `y = pad + (height − v)·scale`, inverse at `:233-236`; `refitTo` `:245`; drag/snap/clamp `:520-528`; area status `:531`; commit gate `:552-565`.
- **Why an SVG modal and not a 3-D handle editor** — its own header, `packages/geometry-wall/src/WallProfileEditor.ts:26-38`: *"there is no camera in this repo guaranteed to be looking at that plane."* A window's elevation frame has the same property; the 3D viewer in the type editor remains the PREVIEW (D8), never the authoring surface.
- **Why not the plan-tool overlay** (`PlanViewToolOverlay.ts`): it is Canvas2D bound to `PlanViewCanvas` + `PlanViewInteraction`, and its `WorldPoint {worldX, worldZ}` vocabulary would have to lie about a `(u, v)` frame. `SvpPlanToolOverlay` proves the handler interface is surface-agnostic, but no `PlanSurface` abstraction exists; extracting one is more work than the profile editor needs and buys nothing here.

**What must be generalised, and where it lives (8-layer rule):**
1. **L2 — the frame, not the code.** `WallProfileEditorSubject/Callbacks/Port` become an elevation-outline subject/port (`{u, v}` + `length/height` extents) that both the wall profile and the window outline use. It STAYS in `packages/geometry-wall` (L2) — `ui-base` is L3 and the file already records that refutation at `apps/editor/src/ui/WallProfileEditor.ts:47-51`; `geometry-window` imports it from there.
2. **L2 — the modes the founder means by "any polygon".** Today the editor only DRAGS an existing ring. Click-to-place polyline (Enter closes), ⛔ ORTHO absolute, and 3-click arcs are fed from the already-pure primitives the boundary-line tool uses — `boundaryPath.ts:136 resolveBoundaryVertex`, `boundaryArc.ts:79 arcSegmentThroughMidpoint` (16 chords, recoverable by `resolveBoundarySegments`), `orthoConstraint.ts:84 orthoConstrainXZ` — through a `{u, v}` ↔ `{x, z}` adapter. **Never a copy**: `CurtainWallTool.ts:105`'s rival `ARC_SEGMENTS = 10` is the cautionary case.
3. **L2 — validation** reuses `WallProfile.ts:243 PROFILE_MIN_VERTICES`, `:246 PROFILE_MIN_AREA_M2`, `:306 wallProfileSignedArea2`, `geometry-kernel/src/pure/pointInPolygon.ts:209 pointInPolygonXY`, `geometry-kernel` `findSelfIntersection` — as D3's ONE predicate.
4. **L7 — the surface.** The SVG surface + `makeDraggable`/`makeResizable` wiring is EXTRACTED so the wall profile modal and the window outline section are two callers of one surface (both keep their behaviour, pinned by the wall profile editor's existing tests). Mounted from `FinishTypeEditorModal.ts` next to the grid block (`:606-651`), declared in `ElementTypeAuthoringRegistry.ts` as `finishEditor.outline` — a declaration, never a family branch (C65 §3.5). P6 split kept: the surface hands a ring to `onCommit`; the caller dispatches the command.
