### 1b. What IS a corruption risk — the wipe guard is inert on the exact two paths it exists for

`apps/editor/src/ui/platform/PlatformShell.ts:297` reads `versionRepository.getLatestVersion(id)`. The "No local versions — clearing scene before data restore" branch (`:319`) is entered **only when that returned null**. Inside the empty-load `.then` the autosave fence is dropped at **`:349-350`** (`setLoading(false)` then `resetDirtyAfterLoad()`) and only *then* does it await the IDB warm and `_loadLatestVersionFromServer(id)` (`:376`).

When an autosave fires in that window, `PlatformSaveController.ts:299` asks for the baseline with **the same call** (`versionRepository.getLatestVersion(this.ctx.projectId)?.elementCount ?? null`) — still null, because reaching the server leg *proves* the warmed re-read was also null. `saveWipeGuard.ts:118-124` then returns `{action:'write', code:'no-stored-baseline'}` and an **empty snapshot is written as the newest LOCAL version**.

The two outcomes are mutually exclusive by construction, which is what makes the guard unreachable rather than merely weak: either the server record landed (then `saveVersionWithMeta` created a real baseline *and* `loadVersion` called `setLoading(true)`, cancelling the debounce), or it did not (fence down, baseline null).

The arming mutation is the founder's own "default views created three times": `ClearProjectCommand.ts:212` → `viewDefinitionStore.reset()` → `vd:store-reset` → a 300 ms `ensureDefaultViews()` timer that the empty snapshot cannot cancel, because `_makeEmptySnapshot` writes `viewDefinitions: []` (`PlatformShell.ts:402`) and `ViewDefinitionStore.deserialize` early-returns on a bare array without dispatching `vd:store-loaded`. Six `vd:view-created` events land ~260 ms into the unfenced window; `vd:view-created` is in `SaveOrchestrator`'s MUTATION_EVENTS; `viewDefinitions` is in the serialized snapshot so the hash check cannot suppress the write.

**Net: if the server leg exceeds the ~4 s settle deadline — or, worse, resolves fast with nothing usable — an empty autosave is written as the newest local version.** `ProjectRepository.getLatestVersion` takes the last container entry, and `PlatformShell:297-300` prefers that local record over the server unconditionally on every subsequent open. From then on the guard reads `stored-also-bare` and every further empty write is allowed. The durable server copy is protected (`server/emptySnapshotGuard.js` via `server.js:3796+`, 409) — which is exactly the split L-10040 predicted: *"A server-only guard protects the durable copy and still restores an empty project from IndexedDB forever."*

**Did it fire on this run? No.** `[VersionRepository] reason=save-version — 1 version(s) persisted` prints `entries.length` after the write, so the ring held zero versions before it — independent confirmation the baseline was null at guard time — and the server leg was fast enough that `loadVersion`'s `setLoading(true)` cancelled the debounce first. **The founder got lucky on the network, not on the code.**

## 3. The crash — shadow-texture device loss

### First, a submitted root cause that is REFUTED, so nobody implements it as written

The claim was an ordering **asymmetry**: the interactive path wrapped in a guard, the load path bare. **Both halves are false.**

- **The load path IS frozen.** `initScene.ts:3580` defines `_freezeShadowForLoad()` (§FIX-SHADOW-LOAD-TIER-DESTROY, L-39), armed at `:3607` — one line before the `renderPipelineManager.onProjectSwitch()` the founder's log shows, so it demonstrably fired on this run. It is released only by `_thawShadowAfterLoad()` (`:3586`, called at `:3738` from the `pryzm-project-loaded` handler), whose actual pop sits inside `setTimeout(…, 0)`. The deferred load shadow pass is registered later (`:4174`) and is synchronous, so it executes with `_shadowReallocFreezeDepth > 0`. The other door, `pryzm-load-suppress-end` (`:4177`), fires from inside `ProjectLoader.load()`, even earlier. The load window is **wider** than the interactive one, not absent.
- **The freeze is the wrong lever for this class anyway, and the repo says so.** `RenderPipelineManager.ts:2276-2291`: *"`setShadowReallocFrozen` … set `autoUpdate=false`, which suppresses the depth PASS. That is exactly the right lever for a `mapSize` realloc… A CASTER-SET change is a different failure… `autoUpdate=false` cannot defer it, because there is no depth pass left to defer."* `_armWallCommitShadowFreeze()` (`:4058`) is nothing but that same freeze. **Neither** path uses `runShadowCasterMutation`. Also: §MESH110-SHADOW-POLICY (`0e4aa0d7`) is dated **2026-08-26**, not 2026-09-06 — 14 days before the crash, not three.

### What IS established

1. **The mechanism class.** A shadow-owned depth target is freed inside three's own `render()` while a submit referencing it is still in flight. `ShadowNode.js:396` names that texture `'ShadowDepthTexture'` verbatim; `AnalyticLightNode.js:259-273` and `ShadowNode.js:617-621` (`_currentShadowType` mismatch → `_reset()` → `shadowMap.dispose()`) are the two doors.
2. **Three real unordered or unfenced windows on this exact path:** the derived detector is blind to per-object `receiveShadow`, which is the third input to three's own render-object cache key (fix #8/#9); mesh shadow flags have no boundary funnel while light flags and map reallocs both do (fix #9); the shadow rebuild has no project epoch and `dispose()` never clears its timer (fix #10).
3. **The recovery ladder spent both attempts on a byte-identical repair** and its own §L-10012 log says so (fix #11).

### What is NOT established — the door that actually fired

## 4. The 3.4 seconds — how much the yield fix actually recovers

**The label is false: `curtain_walls=3406.3ms/n=0` does not measure curtain walls.** `ImportProjectCommand.executeChunked` (`:409-421`) is `while (!step.done) { await yieldFn(); step = gen.next(); }` — the frame bus is awaited on **every** resume — and `__step(name, n)` (`:452-468`) closes the previous step and opens the named one, with three suspension points sitting between the open and the close (`:1071→:1074`, `:1104→:1107`, `:1215→:1218`). - `3 × avgWait 1443.7 = 4331.1` = `waiting`, exactly.

- `furniture 411.1 + roofs 515.1 = 926.2` vs `4331.1 − 3406.2 = 924.9` → **1.3 ms** of real work across both.

**Why the felt number is a band and not a number.** The render/PSO work in those windows is un-serialised, not deleted — the scene must still be drawn once. Two sub-candidates, both with in-repo measured precedent:
