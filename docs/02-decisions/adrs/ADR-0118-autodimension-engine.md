## Context

PRYZM already owns **both halves** of an auto-dimensioning system — but nothing in between:

- **The output half.** The L0 `DimensionString` schema (`packages/schemas/src/annotation/dimension.ts`) with element+anchor references, chain/overall discriminators, provenance flags, and placement offsets; `produceDimensions` (`packages/geometry-kernel/src/dimensions/producer.ts`) that emits them; `evaluateDimensions` that resolves them to world-mm; and the `PlanViewAnnotationRenderer` plan-canvas draw loop. This half knows how to *draw* a dimension.
- **The input half.** A wall connectivity graph in `JunctionResolverV2.detectJunctions` (the ADR-0055 P1 graph, with all the founder-hardened L/T/X junction fixes); a planar-face perimeter + room tracer in `PlanarTopologyEngine.computeTopology`; and per-wall opening spans in `WallOccupancyStore.getOccupiedSpans`. This half knows the *geometry* to be dimensioned.

**The gap is the intelligence layer.** Today's `produceDimensions` is a naive per-element emitter: it walks `walls[]`/`doors[]`/`windows[]`/`rooms[]` and emits one `DimensionString` per element — a wall length here, an opening width there, a room bbox there. It does **no** graph traversal, **no** collinear grouping, **no** chain assembly, **no** overall span, **no** placement/stacking, **no** conflict resolution, and **no** QA. The result is exactly the defects an architect rejects: two collinear walls across a façade get two independent length dims that neither chain nor share a datum; every opening gets a width but no *location*; nothing guarantees the opening widths + piers sum to the wall length; and nothing prevents two dims landing on the same line. The `set-out` mode is closer to architect intent (offset-from-datum + width + overall) but is still a blind per-opening emission that explicitly disclaims resolving along-wall geometry.

Architects need **construction-ready** auto-dimensions — a complete, non-redundant, non-overlapping, QA-validated SET — and they need it to be **deterministic**: a stamped drawing cannot have its dimensions reshuffle between runs, and the same plan must always document identically. This rules out an AI/ML/LLM dimensioner. It is a computational-geometry planning problem, and PRYZM already has every primitive it needs.

C24.1 (Auto-Documentation Sheets) is blocked on exactly this: it needs a "DS5+" dimension provider that produces a planned, QA'd set rather than the naive set-out emission.

## Decision

**Build `@pryzm/auto-dimension` — a new L2 PURE engine implementing a deterministic 8-stage pipeline that turns an element snapshot into a complete, deduplicated, stacked, QA-validated `DimensionString[]`.** It supersedes the intelligence-free `produceDimensions` per-element/set-out modes (which become thin fallbacks) without changing the output schema or the render/persist sinks.

- **Pure, L2, deterministic.** The engine is a DTO→DTO function: zero THREE (P2), zero DOM (P4), zero I/O, zero RNG. The only non-pure-domain import is `@opentelemetry/api` (spans, P8). Same input geometry → byte-identical output (ADR-0061); no `Math.random`/`Date.now`; total orders everywhere with a ULID final tiebreak.
- **Reuse, don't rebuild.** Stage-1 connectivity reuses `detectJunctions` (the ADR-0055 P1 graph — so ticks land exactly where wall miters land) and `computeTopology` (perimeter + room rings). Stage-2/3 reuse `WallOccupancyStore.getOccupiedSpans`. The output is the existing L0 `DimensionString`; the sink is the existing command + render loop. The engine invents no new numerical primitive — it composes the line-intersection / perpendicular-projection / collinear-test helpers that already exist.
- **The 8 stages** (C56 §1.2): (1) connectivity graph + perimeter, (2) segmentation, (3) opening analysis, (4) chain planning via a registry of pure string-planners, (5) chain geometry resolution to datum-axis tick lists, (6) rule-based placement/stacking, (7) conflict resolution (dedupe/merge/bump/push — never RNG), (8) QA validation → `AutoDimReport`.
- **Executor-only mutation (P6).** The pure engine emits data. A thin editor-side executor `applyAutoDimensions` (`apps/editor`, L5 — the only impure surface) gathers the snapshot, calls the pure planner, and dispatches the emitted strings through the command bus inside **one** `batchCoordinator.runBatch` so a whole SET is a single undo (C11, C24.1 §1.2).
- **Phased P1→P4.** P1 — exterior wall-chain + located/sized openings on rectangular + L plans (overall + exterior chain + opening chain, single-row). P2 — multi-row stacking, text-overlap bump, geometry-crossing push, dedupe (DR-1/DR-2), tiny-fragment merge, angled/T/parallel edge cases. P3 — interior room chains via `computeTopology.rooms`. P4 — the "documentation core": grids, columns, sections, elevations, curtain-wall panels, curved-wall chords/radii, plus lifting the shared pure `planar-topology` core.

The normative invariants live in C56; the engineering design in SPEC-AUTODIMENSION; the authoritative design in the SPIKE (commit `842dc2be`). This ADR records *why a deterministic pure engine* over the alternatives.

## Consequences

- **Positive.** PRYZM gains a **deterministic documentation core**: construction-ready, non-redundant, QA'd dimension sets that are reproducible and reviewable. It reuses both existing halves (input graph + output schema/render) with **zero schema churn** and no new viewer. The string-planner registry makes it **extensible** — grids, columns, sections, rooms, elevations are new planners, never changes to placement/conflict/QA, feeding directly into the C24.1 auto-documentation SET. Purity keeps it node-testable and CI-enforceable (a determinism self-check + purity gate). Reusing the ADR-0055 P1 junction graph guarantees dimension ticks and wall corners agree (no visual drift).
- **Negative / trade-offs / risks.** Placement + conflict resolution are genuinely hard: side selection, multi-row stacking, text-overlap and geometry-crossing resolution are the bulk of the engineering (P2 scope) and a v1 overlap must be accepted-and-logged, never RNG-escaped. Achieving one-undo requires a **new `dimension.createMany` batch verb** (C56 §2) so the executor does not do N handler round-trips — the open sink/verb decision (SPIKE §18 Q1) gates P1. A THREE-taint risk exists reaching `computeTopology` through the `room-topology` barrel; P1 must build a pure `{x,z}` wall graph in-package (or fast-track the P4 pure `planar-topology` lift), verified by the purity gate. The as-shipped `detectJunctions` clustering is `O(n²)` — bounded per-level but the one super-linear hot spot (mitigated later by the existing spatial index).
- **Determinism obligation.** Every merge/repositioning decision is a total order with a ULID tiebreak; a byte-identical re-run is asserted in tests (QA-6). This is a permanent maintenance constraint on the subsystem: any future planner MUST preserve it.

## Alternatives considered

- **Extend the naive `produceDimensions` producer in place.** Rejected: the producer has no graph, no run/collinear grouping, no chain assembly, no placement/stacking, no conflict resolution, and no QA — the exact missing intelligence. Bolting planning onto a per-element emitter would entangle the emission and the planning, defeat the pure string-planner registry, and still not give an overall span or a deduplicated set. The producer is kept as a thin fallback for free-standing elements (rank-5), not the planner.
- **An AI / ML / LLM-based dimensioner.** Rejected: it violates the core objective — construction documentation MUST be deterministic and reproducible (an architect stamps it; the same plan must document identically every run). An AI dimensioner is non-deterministic, unauditable, and cannot guarantee the completeness invariants (every opening located+sized, no distance twice, no gaps). Dimensioning is a solved computational-geometry problem for which PRYZM already owns every primitive; statistical inference adds risk and removes the guarantee.
- **A single global overall-only auto-dimension (bounding box only).** Rejected: an overall AABB is trivially derivable but is not documentation — it locates nothing, sizes no opening, and dimensions no wall break. It fails DI-2/DI-3 and does not unblock C24.1.
- **Persist raw-point dimensions only (no live element+anchor refs).** Rejected: raw-point dims do not re-evaluate when a wall/opening moves, so the documentation goes stale on the first edit. The engine emits element+anchor `DimensionReference`s (staying live); the executor adapts to the raw-point `dimension.create` payload via `evaluateDimensions` only at the sink.
