# ADR-0074 — Solar HEAT / sun-hours runs client-side on WebGPU over the REAL model geometry (heatmap on roofs & façades), built on RealSunService

- **Status:** Proposed — 2026-06-16
- **Layer:** L1 GPU pass in `packages/renderer-three/` (single THREE owner, P2) + a new L2 pure package `@pryzm/solar-analysis` (sun-set generation + accumulation orchestration, no THREE) consuming the C21 Climate substrate via `runtime.climate`.
- **Relates to:** ADR-0064 (in-browser wind CFD on WebGPU+LBM — the sister env-sim precedent), ADR-0007 (WebGPU/WebGL2 dual-mode — the rendering substrate + fallback tiering), ADR-0070 (Project-North vs True-North authoring frame — orientation of the sun relative to the model), §DIAG-DAYLIGHT (the existing read-only per-room daylight pass this generalises from rooms-as-polygons to real surfaces).
- **Contracts:** C21 (Climate Ingestion — owner of solar position + irradiance magnitude; this ADR proposes a new **C21 §10 Solar Exposure & Sun-Hours Analysis** section, NOT a new contract), C04 (Rendering & Scheduling — THREE/rAF ownership), C12 (Geospatial — lat/lon → LTP-ENU scene frame + orientation), C45 (Browser & Device Matrix — WebGPU tiering + fallback), C22 (Privacy & PII — no data egress), C10 (Performance & Observability — perf budgets + P8 spans). No contract is rewritten; C21 gains a section (see *Contract alignment*).

## Context — the ask and the gap

The user asked for **real solar HEAT / sun-hours environmental analysis**: GPU-accelerated **sun-hours** (and incident solar irradiance) computed on the **actual building roofs and façades**, painted back onto the model as a **heatmap**, with GPU shadow occlusion, glass transparency (transparent surfaces partially occlude), and a **real** sun position, all running **in the browser**. The explicit reference is **ThatOpen Company's WebGPU solar demo**: sun-hours on real roofs/façades over a ~1.4M-triangle model, with time/day/latitude sliders and AVG/MAX/MIN sun-hours readouts. As instructed, this ADR was written **after** reviewing the governing contracts, specs, and ADRs (C21, C12, C04, C45, ADR-0064, ADR-0007) and the existing sun/daylight plumbing.

### What PRYZM ALREADY has (the substrate to build ON)

- **Real sun position — `RealSunService`** (`packages/core-app-model/src/rendering/RealSunService.ts`). A full **NOAA solar-position algorithm** (`computeSolarPosition`, file:81–144) computing altitude + azimuth from `(lat, lng, date)`, ±0.5° accurate; it manages a single `THREE.DirectionalLight` (`SUN_LIGHT_NAME`, file:67) with a 2048² shadow map (`SUN_SHADOW_MAP_SIZE`, file:70), imports THREE **only** via `@pryzm/renderer-three/three` (file:31), and per its header contract NEVER mutates a store — it operates purely on the Three.js projection layer. C21 §1.3 + §3.3 already designate this as the canonical `SolarPathReader` (solar position is **computed, never stored**). The time/lat/lng slider UI already exists in `apps/editor/src/ui/rendering/RealSunControl.ts` (`setTime`, `setLocation`).
- **Existing daylight scoring (the polygon-level precursor).** `apps/editor/src/ui/daylight/daylightConsole.ts` exposes `window.pryzmComputeDaylight()` (§DIAG-DAYLIGHT), a **read-only** per-room pass that assembles `RoomDaylightInput[]` from detected rooms + their exterior-wall window openings and runs `computeBuildingDaylight(inputs, defaultSunSamples(lat))` (`packages/ai-host/src/workflows/daylight/daylightAnalysis.ts`). It scores rooms as **polygons with apertures** using a default sun-sample set; it does NOT touch real surface geometry or GPU occlusion. `aspectFromSunDir(latDeg)` (`packages/ai-host/src/workflows/houseLayout/stairPosition.ts:731`) is the layout engine's coarse cardinal-sun heuristic. These are CPU, room-resolution, geometric-only — the proposed pass is their per-triangle, GPU, occlusion-aware generalisation.
- **WebGPU env-sim precedent — ADR-0064 / C54.** PRYZM has already decided to run a heavy environmental simulation (wind CFD) **client-side on WebGPU compute**, no cloud, no queue, with a **graceful soft-fallback** when WebGPU is absent (C54 §1.2) and a **BETA / partially-calibrated honesty rule** (C54 §1.1). That ADR's architecture, risk handling, and fallback discipline are directly reusable here.
- **Single THREE / GPU owner — P2 + C04.** `import * as THREE` is allowed **only** in `packages/renderer-three/`. Any GPU solar pass (shadow map, compute ray pass, heatmap material) therefore MUST live in `renderer-three`. ADR-0073 restates the same invariant ("geometry stays in `renderer-three`").
- **Site coordinates — C12 + ProjectLocation.** `(lat, lon)` resolves to the LTP-ENU scene frame via `packages/geospatial/src/LTPENURebase.ts` (C12 §1.1); the site location lives in `packages/schemas/src/site/SiteLocation.ts` (+ `legacyProjectLocation.ts`). ADR-0070 owns Project-North vs True-North, i.e. the rotation that aligns the model's authoring frame to the true compass the sun is computed in.
- **Climate substrate — C21 (DRAFT).** `runtime.climate` (`ClimateStore.sampleSun`, `SolarPathReader.sampleYear`) already supplies per-hour solar samples and, for sites with ingested EPW, real `directNormalWm2` / `diffuseHorizontalWm2` / `globalHorizontalWm2` (C21 §2.2 `EPWRecord`) — exactly the irradiance MAGNITUDE the heat model needs.

### The GAP

PRYZM computes real **sun direction** and scores daylight at **room-polygon** resolution, but has **no per-surface, GPU-occluded, model-wide sun-hours / irradiance pass**: nothing sums "how many hours does *this* roof facet / *this* façade panel actually see the sun across a day or year, accounting for self-shadowing and neighbours," and nothing paints that back as a heatmap on the real mesh. The ThatOpen demo is exactly this missing surface. C21 §9 explicitly **defers** CFD (§9.b) and microclimate/UHI (§9.c) but says **nothing** about per-surface solar exposure / sun-hours — it is an un-owned gap that sits naturally on top of the C21 solar substrate.

## Decision

**PRYZM computes solar sun-hours and incident irradiance CLIENT-SIDE on WebGPU, directly over the real model triangles, with GPU shadow occlusion and glass-transparency attenuation, surfaced as a heatmap overlay on the model with time/day/solstice/latitude sliders and AVG/MAX/MIN readouts — built ON TOP of `RealSunService` (real sun) and the C21 Climate substrate (irradiance magnitude), inside `renderer-three` (P2).**

### Architecture

1. **Sun set — real sun, sampled over time.** A pure L2 helper in a new `@pryzm/solar-analysis` package generates the **sun-sample set** for a run: one sun direction per time sample, computed from `RealSunService`'s NOAA algorithm (reused via the C21 `SolarPathReader.sample` / `sampleYear`) for `(lat, lon)` at each `dateTimeUtc` in the requested window (a single day at N-minute steps, or a year sampled per ASHRAE/typical-day cadence). Below-horizon samples are dropped. The model's orientation relative to true north comes from ADR-0070 (Project-North → True-North), and lat/lon comes from C12 / `SiteLocation`. This package is **THREE-free and pure** (P5-style), so it is unit-testable and deterministic (a sun set is reproducible per `(lat, lon, window, step, frame)`), and it is the only place that touches `runtime.climate`.

2. **GPU occlusion — shadow-map accumulation (P1) or a compute ray pass (P3).** For each sun direction in the set, the model is rendered from the sun's viewpoint into a depth/shadow map (reusing the `RealSunService` DirectionalLight shadow path as the proven primitive); each surface fragment tests itself against that shadow map. A fragment that is lit at sample *k* contributes `Δt` hours (the per-sample time slice). Accumulating across all samples yields **sun-hours per fragment**. This is the same "render-from-light, test-occlusion" primitive the viewport already runs, looped over the sun set and accumulated into a per-surface buffer (render-target or storage texture) — the WebGPU path uses a compute accumulation; the WebGL2 fallback uses additive render-to-texture (ADR-0007 dual-mode).

3. **Glass transparency.** Transparent surfaces (curtain wall glazing, windows) **partially** occlude: instead of a binary shadow test, glazing fragments attenuate the accumulated contribution by a transmittance factor (per-material, sourced from the glazing material/system type), so a façade behind glass receives reduced — not zero — sun-hours. This is a shadow-pass material variant (an alpha/transmittance-aware occluder), not a new solver.

4. **Sun-hours accumulation + irradiance magnitude.** Two distinct quantities, kept explicitly separate:
   - **PURE geometric sun-hours** (P1) — needs **no external data**: just sun geometry + occlusion. Units = hours of direct-beam exposure over the sampled window. This is the ThatOpen-equivalent metric and ships first.
   - **Irradiance MAGNITUDE** (P2) — needs a **climate source** for the actual W/m² hitting each surface (beam + diffuse + cosine-of-incidence + atmospheric attenuation). The source is the C21 `ClimateDataset` (`directNormalWm2` / `diffuseHorizontalWm2` per `EPWRecord`); candidates when no EPW is ingested are PVGIS, NOAA/NCEI, or a typical-meteorological-year (TMY) generator. When climate is only `'fallback-defaults'` (C21 §1.2), the pass MUST refuse to report absolute kWh/m² and degrade to **geometric sun-hours only** (the §DIAG-DAYLIGHT honesty pattern + the C21 §5.3 climate-quality gate).

5. **Heatmap overlay material.** The accumulated per-surface buffer is mapped through a colour ramp (e.g. blue→red) into an **overlay material** on the model — a `renderer-three` material/pass that reads the sun-hours/irradiance texture and tints the real mesh. It is a **visualisation overlay**, never a store mutation (mirrors `RealSunService`'s "projection-layer only, never mutates a store" contract).

6. **Slider UI + AVG/MAX/MIN readout.** Extend the existing `RealSunControl` pattern (`apps/editor/src/ui/rendering/`) with time / day / solstice-preset / latitude controls bound to the sun-set window, plus an AVG / MAX / MIN sun-hours readout reduced from the accumulation buffer. UI is read-only and talks to the pass through the rendering-pipeline coordinator (the RealSunControl convention), dispatching no commands.

### Package shape

- **`@pryzm/solar-analysis`** (NEW, L2, THREE-free, pure): sun-set generation from `RealSunService`/C21, accumulation orchestration, the AVG/MAX/MIN reducer, deterministic + spannable (P8). Depends on `packages/schemas` (L0) + reads `runtime.climate`. Re-exports nothing into `plugin-sdk` initially.
- **`packages/renderer-three/`** (EXTEND, L1): the actual GPU work — the per-sun shadow/occlusion pass, the WebGPU compute (or WebGL2 additive) accumulation, the transmittance-aware glazing occluder, and the heatmap overlay material. This is where THREE/WebGPU live (P2 / C04). `renderer-three` is *invoked by* `@pryzm/solar-analysis` for orchestration but owns all GPU resources.

## Contract alignment

- **Owner: extend C21, do NOT mint a new contract.** Solar position is already C21's (§1.3 "Solar position is COMPUTED, never stored"; §3.3 `SolarPathReader`) and irradiance magnitude is already C21's data (`EPWRecord.directNormalWm2` etc., §2.2). Per-surface sun-hours / irradiance is a **derived consumer** of that substrate — exactly the C21 §1.10 "consumer derives discipline-specific quantities" pattern. The right home is a new normative section **C21 §10 — Solar Exposure & Sun-Hours Analysis** (invariants: geometric sun-hours need no climate; absolute irradiance requires a non-`fallback-defaults` tier per §1.2; the pass is read-only/overlay-only and emits a `pryzm.climate.solarExposure` span per §1.6; results are deterministic per sun-set frame for C23 provenance). A brand-new contract would fork solar ownership away from C21 and is rejected for the same reason ADR-0064 put its CFD invariants in C54 rather than re-deciding C21's wind rose.
- **P2 single THREE owner — confirmed mandatory.** The shadow map, the WebGPU compute pass, the glazing occluder, and the heatmap material all touch THREE/WebGPU, so by P2 + C04 they MUST live in `packages/renderer-three/`. `@pryzm/solar-analysis` stays THREE-free and orchestration-only. This is the same split ADR-0073 enforces ("geometry stays in renderer-three").
- **Geospatial PG0 phase.** This lands as a PG0-family deliverable alongside C21's PG0.5 (climate-host) and the geospatial foundation programme (now realised as C19/C20/C21). Geometric sun-hours (P1) needs only C12 (lat/lon → scene) + `RealSunService` and can ship ahead of full EPW ingestion; irradiance magnitude (P2) is gated on C21's `ClimateStore.resolve(siteRef)` returning a non-fallback tier.

## Consequences + phased plan

**Phased plan:**

- **P1 — Geometric sun-hours on GPU (no external data).** Real sun from `RealSunService` over a sampled day; GPU shadow-map occlusion looped + accumulated per surface; heatmap overlay material; time/day/solstice/latitude sliders + AVG/MAX/MIN readout. WebGPU compute accumulation with a WebGL2 additive-render fallback (ADR-0007). This is the direct ThatOpen-equivalent and the demoable milestone. No C21 dependency beyond the shared solar algorithm.
- **P2 — Glass + irradiance magnitude from climate.** Transmittance-aware glazing occluder (partial occlusion through glass); absolute W/m² / kWh-per-m² from the C21 `ClimateDataset` (EPW beam+diffuse, cosine-of-incidence), with PVGIS / NOAA / TMY as the no-EPW candidates; the climate-quality gate (C21 §5.3) forces a graceful "geometric-only" degrade on `fallback-defaults`.
- **P3 — Per-room heat-gain rollup + AI integration + compute ray pass.** Reduce per-surface irradiance into per-room solar heat-gain (feeding the Cognition-Stack environmental drivers / facade-value field), optionally upgrade occlusion from shadow-map to a WebGPU compute **ray** pass for very large meshes, and expose the result to site-aware AI workflows (window-type / shading / orientation recommendations) — the same way ADR-0064's CFD feeds the `naturalVentilation` driver rather than a parallel objective.

**Positive.** Free + fast + local (no cloud, no queue, no data egress — a C22 win by construction, same as ADR-0064); reuses the existing real-sun algorithm, the DirectionalLight shadow primitive, the C12 site frame, and the C21 climate data; generalises the existing room-polygon §DIAG-DAYLIGHT pass to per-surface truth; keeps all GPU work behind the single P2 owner.

**Negative / trade-offs.** WebGPU is opt-in / still rolling out (C45) → a real subset of users get only the WebGL2-fallback (lower-resolution / slower) path, or geometric-only when climate is absent; per-surface accumulation over a ~1.4M-triangle model with many sun samples is a genuine perf load (cite ADR-0064: heavy env-sim is *tens of seconds* class, not per-frame) and needs LOD / sample-count budgeting per C10; an indicative geometric sun-hours figure is **not** a certified solar/energy analysis, so the ADR-0064 / C54 **BETA + honesty** rule applies — absolute irradiance MUST be labelled with its climate-data tier (EPW vs NOAA vs none) and MUST NOT be presented as compliance-grade without a real climate source. A new pure package + WGSL/GLSL passes + a heatmap material is real engineering effort.

**Determinism.** A run is reproducible per `(lat, lon, window, step, model-hash, lattice/sample frame, climate dataset version)` so the result can be audited (C23) and fed deterministically to the layout / AI engines (the ADR-0064 determinism discipline).

**Risks.** WebGPU availability (mitigated by the ADR-0007 WebGL2 fallback + a geometric-only degrade); perf on large meshes (mitigated by sample-count + LOD budgets, ADR-0064 precedent); mislabelling indicative geometry as certified analysis (mitigated by the C54-style honesty invariant carried into C21 §10).

## Alternatives considered

- **Cloud / server-side solar bake.** Rejected for the same reasons as ADR-0064: infra cost, a job queue + minutes of latency, and shipping site geometry off-device (a C22 privacy + data-egress surface). The founder's pattern (proven for wind CFD) is free/fast/local client-side WebGPU — solar follows it.
- **A brand-new "C-solar" contract.** Rejected: solar position + irradiance data already belong to C21; per-surface exposure is a derived consumer, so it extends C21 §10 rather than forking solar ownership (consistent with ADR-0064 placing CFD invariants in C54, not re-deciding C21's wind rose).
- **Keep only the room-polygon daylight score (§DIAG-DAYLIGHT).** Rejected: room-polygon scoring cannot answer per-roof-facet / per-façade-panel sun-hours, has no self-/neighbour-shadow occlusion, and cannot paint a heatmap on the real mesh — which is precisely the ThatOpen target the user asked for.
- **CPU ray-trace per surface.** Rejected for the interactive case: a per-triangle × per-sun CPU trace over ~1.4M triangles blocks the frame for far too long; the GPU shadow-map / compute path is the only route to interactive sliders. (A CPU path may remain as a last-resort fallback below the WebGL2 tier.)
