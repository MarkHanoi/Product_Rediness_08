# ADR-0119 — The AutoDimension RENDER sink is the subsystem `annotationStore` `'linear-dim'` path, not `dimension.createMany`

- **Status**: Accepted
- **Date**: 2026-07-07
- **Deciders**: architecture team (founder-driven — Issue Log **L-145** / **L-138**, `docs/04-reference/V1-LAUNCH-READINESS-AUDIT.md`)
- **Tags**: `§FIX-AUTODIM-SUBSYSTEM-STORE-SINK`
- **Supersedes (in part)**: [ADR-0118 — AutoDimension is a deterministic L2-pure engine](./ADR-0118-autodimension-engine.md) — specifically the *sink* half of its "Decision → Executor-only mutation (P6)" bullet and its "Negative" note that "achieving one-undo requires a new `dimension.createMany` batch verb". The pure-engine, determinism, purity, 8-stage, and executor-only-mutation decisions of ADR-0118 stand unchanged; only the **render sink** the executor dispatches to is corrected here.
- **Related contracts**: [C56 — AutoDimension Engine](../contracts/C56-AUTODIMENSION.md) (§1.8 layered placement + §2 command surface — amended in place to match this ADR), [C03 — Schemas, Commands & State](../contracts/C03-SCHEMAS-COMMANDS-AND-STATE.md) (command-path-only mutation, P6; CQRS vs subsystem stores), [C11 — Element Creation Pipeline](../contracts/C11-ELEMENT-CREATION-PIPELINE.md) / [C24.1](../contracts/C24.1-AUTO-DOCUMENTATION-SHEETS-PROTOCOL.md) §1.2 (derived creation = one `runBatch` = one undo), [ADR-0002](./ADR-0002-command-handler-signature.md) (handler/affectedStores contract), [ADR-0028](./ADR-0028-plan-view-canvas-architecture.md) (`PlanViewAnnotationRenderer`), [ADR-0061](./ADR-0061-building-graph-bidirectional-edit-substrate.md) (typed ULID ids)
- **Engineering spec**: [SPEC-AUTODIMENSION](../../03-execution/specs/SPEC-AUTODIMENSION.md) (§5 amended in place)

## Context

ADR-0118 shipped `@pryzm/auto-dimension` (a deterministic, pure L2 planner) plus an editor executor `applyAutoDimensions`. ADR-0118 / C56 §1.8 / SPEC §5 all stated the executor dispatches the emitted `DimensionString[]` through a **`dimension.createMany`** command, and that the strings "flow through the existing `evaluateDimensions` → `PlanViewAnnotationRenderer` draw loop". A compliance audit (`docs/03-execution/analysis/compliance-autodimension-2026-07-07.md`, L-138) verified the shipped code against that claim and found the **render seam broken**:

The codebase carries **three** dimension representations, and only one of them renders:

1. **`DimensionString`** (L0 Zod, element+anchor refs) — the engine's output; the sink C56/SPEC/ADR-0118 assumed.
2. **`DimensionData` / `DimensionStore`** (`plugins/dimensions`) — flat point records written by `dimension.create` / `dimension.createMany`. **`PlanViewAnnotationRenderer` never reads this store.** It is dead infrastructure for the render path.
3. **`AnnotationElement 'linear-dim'`** in the **subsystem `annotationStore`** singleton — the ONLY representation `PlanViewAnnotationRenderer.render()` actually draws (via `annotationStore.getByView(viewId)` / `getDimensionsByView`).

The shipped executor already (correctly, per rep. 3) adapted each `DimensionString` into a `'linear-dim'` `AnnotationElement` — but then dispatched it through the **bus verb `annotation.create`**, which is a **text-note** handler: it reads only `id/viewId/kind/anchor/text`, **drops** `geometry2D`+`references`, **rejects** `kind:'linear-dim'` (not in `ANNOTATION_KINDS`), and writes a flat `AnnotationData` into the **CQRS `AnnotationsState`** — a *different* store the renderer never reads. Result: auto-generated dimensions (and the manual `LinearDimPlanToolHandler`, which used the same verb) **did not render**. The one path that DID render — the plugin `LinearDimensionAnnotationTool` — writes the subsystem `annotationStore` via `CreateAnnotationCommand` + the legacy `CommandManager`, not the bus verb.

The subsystem `annotationStore` is a plain singleton (not a CQRS `Store` in the command-bus `storesProvider`), so a modern bus handler cannot cleanly own its patch-routed undo. Its mutation + undo are, by existing design, owned by the legacy command protocol (`CreateAnnotationCommand` → `annotationStore.add/remove`) — the same path every working annotation tool uses and the serializer persists.

The governance rule ("when code disagrees with a contract, the code is wrong — fix the code, or raise a superseding ADR") requires a decision: the contract asserts a `dimension.createMany` → renderer path that does not exist.

## Decision

**The canonical sink for a RENDERED auto-dimension is the subsystem `annotationStore` `'linear-dim'` `AnnotationElement` path, written through the legacy command protocol.** The executor dispatches **one composite `CreateManyAnnotationsCommand`** (new, in `plugins/annotations`) through the `CommandManager` inside one `batchCoordinator.runBatch`, so the whole SET writes to the render store as a **single undo** (C11 / C24.1 §1.2). The manual `LinearDimPlanToolHandler` writes the same store via `CreateAnnotationCommand` (one dim = one undo), mirroring the proven `LinearDimensionAnnotationTool`.

- **Why the subsystem store, not a new/extended bus verb.** The subsystem `annotationStore` is the store the renderer reads and the serializer persists; it is not a CQRS `Store` in the bus `storesProvider`, so a bus handler mutating it would either return empty patches (no undo) or route patches to a store key the ring buffer cannot apply. The legacy `CreateAnnotationCommand`/`CommandManager` already owns this store's mutation + undo (ring-first + `cm`-fallback, per the unified undo path). Reusing it is the least-surprise, P6-compliant path (mutation still flows through a command object, never a direct UI store write) and keeps the executor consistent with every working annotation tool.
- **One undo for the SET.** The `CommandManager` pushes one history entry per `execute`, so a whole auto-dimension SET is batched into ONE composite `CreateManyAnnotationsCommand` (adds all elements in `execute`, removes all in `undo`) rather than N single commands. `batchCoordinator.runBatch` still wraps the dispatch to coalesce the N `storeEventBus` `create` events into one plan re-projection (`skipRedetectRooms` — dimensions bound no rooms).
- **`'linear-dim'` vs `ANNOTATION_KINDS` — reconciled, not "fixed".** `ANNOTATION_KINDS` (11 kinds) is the CQRS `AnnotationsState` `kind` enum for flat text-note-style records; `'linear-dim'` is a **subsystem** `AnnotationType` (26 types) rendered from the subsystem store. A dimension is *not* a CQRS text-note. The correct reconciliation is to STOP routing dimensions through the CQRS `annotation.create` verb (which rightly does not model them) — not to widen `ANNOTATION_KINDS`. The manual handler therefore emits no bus telemetry for dimensions.
- **`dimension.createMany` / `DimensionStore` are RETAINED, not deleted — reclassified.** They remain valid infrastructure for **non-rendered** dimension consumers (schedules, quantity take-off, IFC/export, and any future renderer taught to read `DimensionStore`). They are explicitly **NOT** the render sink and MUST NOT be described as such. The ADR-0055-P1-grounded, deterministic `DimensionString[]` the engine emits remains the source of truth; the executor adapts it to the render representation via `evaluateDimensions` at the sink (unchanged).

## Consequences

- **Positive.** Auto-generated AND manual plan-tool linear dimensions now render on the plan; the executor is consistent with the one proven working tool; the whole auto-dim SET is a single undo; no CQRS/subsystem store split-brain for dimensions; `evaluateDimensions` + the pure engine are untouched (determinism preserved byte-identical). The mandated executor span `pryzm.autodim.apply` and the missing helper/pure-helper spans are added (C56 §1.7, P8).
- **Negative / trade-offs.** The render sink now depends on the **legacy** `CommandManager` (not the modern bus) because the subsystem `annotationStore` is not a CQRS `Store`. Migrating the subsystem annotation store into the bus `storesProvider` (so a first-class `annotation.createElement`/`.createElements` bus verb can own its patch-routed undo) is deferred future work; until then the legacy path is the correct, consistent owner. Persisted annotation ids are minted with `createId('annotation')` (ULID) — deterministic *format* but not byte-identical across runs (the engine's `DimensionString` ids remain deterministic); a fully deterministic persisted set (seed the ULID from the engine's positional id) is a follow-up (L-138 GAP-3).
- **QA-completeness (DI-6) reconciliation.** The engine's `AutoDimReport` records completeness shortfalls as **`warnings`** (e.g. `opening-undimensioned`), which the executor surfaces to the user (toast + console) — satisfying C24.1 §1.3 "no silent omission". C56 §1.3 DI-6 and SPEC §4.4 previously demanded a typed `error` that **rejects** an incomplete SET; this ADR ratifies the shipped intent — **completeness failures are non-blocking, surfaced warnings, not hard rejects** — and amends C56/SPEC in place accordingly. A hard-`errors` reject channel and the run-partition QA-2 (`chain-gap`/`chain-overlap`) detection remain **deferred** (they belong with P2 conflict/stacking); this is a documented follow-up, not a silent gap.

## Alternatives considered

- **Add a first-class bus verb `annotation.createElement(s)` that writes the subsystem store.** Rejected for now: the subsystem `annotationStore` is not a CQRS `Store` in the bus `storesProvider`, so the modern patch/ring-buffer undo cannot route to it; a handler would return empty patches (no undo) or mis-route them. Doing it properly requires migrating the subsystem store into the bus first — larger, riskier, and orthogonal to unblocking the render. Recorded as future work.
- **Teach `PlanViewAnnotationRenderer` to read `DimensionStore` (rep. 2) and keep `dimension.createMany`.** Rejected: it duplicates the annotation render path already shipped for rep. 3, splits dimension state across two live stores + two command families for one user-visible artifact (the exact drift governance exists to prevent), and does not fix the manual tool. Rep. 3 (subsystem `annotationStore`) is already the renderer's single source; consolidate on it.
- **Keep dispatching through the bus `annotation.create` verb (status quo).** Rejected: it is a text-note handler that drops the dimension geometry, rejects `kind:'linear-dim'`, and writes an unrendered CQRS store — the defect itself.
