  [P1] §C111-FAKE-TYPE-CHECKSUM (C111 §2.4, delta D-2)
       `FamilyType.checksum` is typed `sha256:` + 64 hex and is produced by `syncChecksumPlaceholder`
       in file-format/src/family-migrations/ops/split-type.ts — an FNV-1a/32 hash padded to 8 hex
       chars and REPEATED EIGHT TIMES. It passes the Zod `Sha256` regex, its 64 chars are eight
       identical blocks, and it COLLIDED on the 200,000th trivial input ({"Width":65613} vs
       {"Width":77901}). Its own comment says the real sha256 is recomputed by `packFamily`;
       `grep -n "checksum" family-pack.ts` -> NO MATCH, so the fake is written into the signed bytes.
       Nothing anywhere verifies a type checksum. Spec §75 at the format layer.

  [P1] §C111-MIGRATION-EXIT-UNSATISFIABLE (C111 §8.2, delta D-1)
       The `.pryzm-family` migration framework cannot complete a single version bump.
       `MigratorRegistry.register()` throws when from === to; `migrateFamily()` validates the result
       against `FamilyDocumentSchema`, whose `formatVersion` is `z.literal('1.0')`, and `validateExit`
       DEFAULTS TO TRUE. So every legal migrator fails its own exit gate. Executed:
         identityMigrator('1.0','1.1')            -> ok=false "exit schema invalid: expected \"1.0\""
         makeRenameParameterMigrator('1.0','1.1') -> ok=false, same
         same op with { validateExit: false }     -> ok=true, steps=1     (isolates the cause)
         no-op chain (target === source)          -> ok=true, steps=0     (control)
       ⚠ The suite's only green end-to-end migration test passes by writing `formatVersion: '1.0'`
       back into the migrated document, and all eight ops are constructed ('1.0','1.0') and invoked
       via .apply() without ever being registered. The green test is the workaround, not the proof.
       This is the sharp half of D12 — much worse than "formatVersion is not comparable".

  [P2] §C111-UNREACHABLE-FUTURE-VERSION-BRANCH (C111 §8.1)
       `family-unpack.ts` returns `unsupported-future-version` when `formatVersion !== '1.0'`, but
       `FamilyManifestSchema.safeParse` runs first and already returned `manifest-invalid`. Proven:
       '2.0' and '1.1' both fail the parse. A user handed a v2 component file is told their file is
       malformed, not that their PRYZM is old. The one test bearing that name exercises the PROJECT
       format's `unpack`, not `unpackFamily`.

  [P2] §C111-TWO-DEFAULT-CHANNELS (C111 §5.3, delta D-5)
       `FamilyDocument.defaults` is maintained by three migration ops (add-parameter seeds it,
       change-parameter-type converts it, delete-parameter removes from it) and read by NO resolver —
       `resolveParameter` takes {parameters, type, instanceOverrides} and never sees the document.
       C84 EI-9, with the dangerous property that the DEAD channel is the one the framework maintains,
       so it looks alive. Fix = remove the field and the three ops together. Adding a reader is the
       forbidden fix.
